## 1. 密钥落点

**R01 ｜ 中 ｜ 可直接采纳 ｜ e2e 作业是否持有测试库连接**
- 问题：`plan.md:142` 让 e2e "用受限测试网站角色写入、读回、清理"。但凭据表（`plan.md:294`）和 B.7 写的是"CI 常规验证无云端运行凭据""测试库连接信息不放仓库级 Secrets"。
- 风险：e2e 跑的是 PR 提交里的测试代码，`e2e/features/**` 板块可改。放行密钥已是被接受的例外，再放库连接，会把测试 schema 的写权限也交给 PR 代码。
- 修法：写入—读回—清理改由预览应用内一个仅预览可用的探针接口完成。该接口放在受保护的 `src/app/api/debug/**`，要求样本票据，只处理本轮 `runId`。e2e 作业只持放行密钥。同步改 0.8 和凭据表。

**R02 ｜ 中 ｜ 可直接采纳 ｜ D1 `auth` 探针无法验证"用户数无变化"**
- 问题：`plan.md:59` 说探针"只读注入测试配置"。而 `plan.md:98` 规定所有环境都没有 `service_role` 或管理令牌，匿名端读不到用户数。
- 修法：
  - 探针改为断言 `signUp`、对新地址的 `signInWithOtp`、匿名登录都返回"注册关闭"类错误。
  - 用户数由维护者在控制台肉眼核对前后一致，记入 `docs/field-notes.md`。
  - 增加一条负向断言：用匿名 key 经 Data API 访问业务 schema 必须被拒。
  - 关闭用不到的邮箱 OTP、魔法链接和密码找回入口。

**R03 ｜ 中 ｜ 可直接采纳 ｜ 变量清单不全，且板块无法自行补**
- 问题 1：凭据表缺以下几项的落点：
  - 测试用 Alchemy 备用 key。
  - 测试网区块浏览器 key（F2 的源码验证要用）。
  - 测试日记口令（合成值，`plan.md:70` 说测试环境不持真口令）。
  - 工作器的告警通知地址。
  - 收款地址配置（见 R18）。
- 问题 2：`.env.example` 与 `src/lib/env.ts` 是受保护文件，板块不能新增变量，缺变量只能走"需要地基变更"。
- 修法：
  - 0.3 一次列全四个板块要用的变量。例如保留天数、凭证有效期、磁盘和 Turbo 阈值、费用上限、收款配置、浏览器 key。
  - `.env.example` 逐项标注落点：本机、工作器、Preview、GitHub Environment、仅正式。
  - `check-stage0.mjs` 校验：标"仅正式"的变量不得出现在 Preview 和本机清单；`env.ts` 的校验只读自己落点上的变量。
  - 板块只经 `env.ts` 取值。

**R04 ｜ 中 ｜ 【需要你决定】｜ 白名单明文进入开发机环境文件**
- 问题：`plan.md:295` 的本机 `.env.local` 列写"白名单按需"，夜间 AI 读得到真实邮箱。仓库公开，AI 写决策文件或样本时可能带出，而 secretlint 不识别邮箱。
- 推荐：站点只存规范化后邮箱的 SHA-256，比对发件人摘要。开发和 CI 用合成域名邮箱。提供一个 `scripts/` 小工具计算摘要。
- 代价：以后在系统里看不到明文，增删要重算摘要。
- 若不接受：真实邮箱至少只放 Vercel Preview、Production 和测试工作器配置，不进 `~/secrets/<项目>.env.local`。同时做 R29 的扫描。

**R05 ｜ 中 ｜ 可直接采纳 ｜ "夜间 AI 读不到生产服务凭据"的落地方式没写**
- 问题：`plan.md:304` 只说 D3 配沙箱、G2 用探针回报。同一 UID 下，文件 0600 和 `/proc/<pid>/environ` 都挡不住。
- 修法：
  - 生产工作器必须是系统级 systemd 单元，不用用户级单元。
  - 其 `EnvironmentFile` 放 root 属主的 `/etc/` 下，由 systemd 以 root 读取后再降权。
  - 沙箱（bubblewrap、Landlock 或独立 PID 命名空间）隐藏其他进程的 `/proc`，只放行 `~/projects`、本项目 worktree 和测试环境文件。
  - 钱包文件保持已接受的例外，沙箱按此放行。
  - E3 合成秘密演练同时覆盖三条读取路径：读文件、读 `/proc/<pid>/environ`、读 `journalctl` 与 systemd 环境。

**R06 ｜ 低 ｜ 可直接采纳 ｜ 迁移凭据环境与令牌范围**
- `prod-db-admin` 加 Required reviewers（维护者本人）和仅限 `main`。
- E3 断言 `migrate-integration.yml` 不引用该环境（对工作流文本做静态检查）。
- 账号级的 Supabase 访问令牌，D1 确认该账号下只有本项目，或把此范围记为已接受风险。
- 非机密配置（两套 origin、测试项目标识）放 Actions Variables，不写进公开仓库的工作流文件。

## 2. 板块冲突与共用资源

**R07 ｜ 中 ｜ 可直接采纳 ｜ 六个重叠路径的"阶段性所有权"没有机器表达**
- 问题：`plan.md:45` 和 `modules.json` 把 `src/app/page.tsx`、`src/app/maintain/page.tsx` 同时列给 foundation 和 memorial，四个 `jobs.ts` 同时列给 foundation 和各业务板块。guard 若按"任一板块列出即放行"，E3 之后 `fix/foundation-N` 仍能改它们，与 memorial 并行必冲突。
- 修法：
  - guard 加规则："`foundation.json` 为 true 后，这六条只算业务板块所有"。
  - E3 演练一次：foundation 分支改 `src/app/page.tsx` 应被拒。
  - 重生成 `modules.json` 时在 foundation 条目旁用文字说明此规则。

**R08 ｜ 中 ｜ 可直接采纳 ｜ 维护导航条目谁来加**
- 问题：`maintain/page.tsx` 在 E3 后归 memorial，但"投稿待办""永久任务""离线快照"的入口属于其他三块。intake 验收（`plan.md:171`）要从「维护后台」点进「投稿待办」，而 intake 只依赖 foundation，memorial 可能还没合。
- 修法：
  - 地基先交静态的"板块路由注册表"，例如 `src/lib/` 下的固定数组：标题加路径，标题由地基锁定。
  - `maintain/page.tsx` 只渲染注册表，各板块只在自己路径下放页面。
  - F2 的"导航可达全部板块"改为核对注册表与页面一一对应。

**R09 ｜ 中 ｜ 可直接采纳 ｜ 样本作业不得进入真实工作器队列**
- 问题：样本会话走 Mock（`plan.md:86、111`），但工作器统一轮询 `jobs`（`plan.md:116、285`）。若样本作业写入同一测试 schema 的 `jobs`，测试工作器会用沙箱适配器执行合成作业，花真测试币和 Turbo 配额。CI 每次重试都会重复一遍，也属第 4 类问题。
- 修法：
  - `jobs` 加 `sample_run_id`，领任务 SQL 固定 `WHERE sample_run_id IS NULL`（在受保护的工作器里）。
  - 样本作业由预览函数内以 Mock 同步完成。
  - 0.5 加单测：带 `runId` 的作业永不被领取。

**R10 ｜ 高 ｜ 可直接采纳 ｜ 工作器会话锁的键在两个环境间冲突**
- 问题：`plan.md:20` 说"固定 PostgreSQL 会话锁，每环境单实例"。测试和生产在同一个 Postgres 库里，advisory lock 是库级的。若两环境用同一个常量键，先启动的占住，另一个永远拿不到。正式工作器上线后会静默空转，不报错。
- 修法：
  - 键由环境推导，例如 `hashtextextended('memorial-worker:' || <schema>, 0)`。
  - 迁移串行锁同样按 schema 分键。
  - 0.5 加测：两环境工作器同时启动都能持锁，同环境第二个实例被拒。

## 3. 板块 0 遗漏的共享机制

**R11 ｜ 高 ｜ 可直接采纳 ｜ 工作器代码怎么到达、怎么更新，计划没写**
- 问题：`plan.md:117` 只说"以 agent 开机启动，目录分开"。没有任何一处写谁在 `integration` 合并后更新测试工作器、生产工作器怎么升级。
- 后果：E3、F2 的真链路可能跑旧代码，或者夜间 AI 往生产目录 `git pull`。
- 修法：
  - 地基交受保护脚本 `.ai/bin/deploy-worker.sh <test|prod> <SHA>`。流程：取指定 SHA 到 `~/deploy/<env>/releases/<SHA>`，`pnpm install --frozen-lockfile`，原子切换 `current`，等持锁任务空闲后重启。
  - 测试工作器只追对应 `integration-schema` 成功的 SHA。
  - 生产工作器只在 G2 由维护者手动部署，迁移先于重启。
  - 单元文件改为模板 `memorial-worker@.service`（实例名 test 或 prod），`modules.json` 的单文件路径同步改。

**R12 ｜ 高 ｜ 可直接采纳 ｜ 数据库连接拓扑没有按客户端写明**
- 问题：`plan.md:20` 只对工作器写了"直连或会话模式"。免费 Supabase 的直连通常只有 IPv6，Vercel 函数和 GitHub 托管 runner 都是 IPv4，以实测为准。迁移、类型比对和体检都在 GitHub 上跑，用错连接方式则整条迁移流水线连不上。
- 修法：在 0.2 写一张连接矩阵，D1 的 `readiness` 探针对每条路径各测一次。
  - Vercel 网站：事务模式池。不用会话级 `SET` 和 advisory lock，`search_path` 用角色级默认。
  - Contabo 工作器：直连（若有 IPv6）或会话模式池，用会话级锁。
  - GitHub 迁移、类型、体检：会话模式池。迁移事务内用 `pg_advisory_xact_lock`。
  - 自定义角色经池登录时的用户名写法以实测为准。

**R13 ｜ 中 ｜ 可直接采纳 ｜ 磁盘 80% 和 Turbo 余额告警没有代码归属**
- 问题：`plan.md:71` 是 D1 配置项，但没有板块或路径负责检测和发送。`foundation` 只能写 `.ai/bin/systemd/memorial-worker.service` 这一个 `.ai` 文件，`.ai/` 又是受保护路径。
- 修法：
  - 地基在 `src/features/foundation/**` 交一个通知适配器，含 Mock。
  - 地基增加定时检查：磁盘用量，以及 Turbo 余额对比阈值。
  - 单元文件（含告警定时器）放进 foundation 的 `writablePaths`。
  - 用模拟阈值演练，沿用 D1.3 的做法。

## 5. 不可逆与高风险操作

**R15 ｜ 高 ｜ 【需要你决定】｜ 自动部署任务由谁、凭什么写入**
- 问题：`plan.md:237` 说"发布记录绑定审核 SHA……工作器只接受自己的发布记录"，但没写发布记录由谁创建。若由 GitHub 作业写库，需要把库写凭据放进 GitHub，违反 B.7。若由 AI 能触及的路径创建，主网自动部署就失去人的锚点。
- 推荐方案（不增加凭据）：
  - 发布记录等于维护者手动运行 `deploy-worker.sh prod <SHA>` 后，生产工作器启动时对自己检出的产物哈希和构造配置的确认。
  - `main` 只有维护者能更新，所以"`main` 上出现新产物哈希"本身就是人的授权。主网仍受两个开关和 `ALLOW_MAINNET` 管。
  - 测试网同理，用 `integration` 上 `integration-schema` 通过的 SHA。
- 请回答：是否采用？若不采用，请指定发布记录的写入者及其凭据落点。

**R16 ｜ 中 ｜ 可直接采纳 ｜ 部署的前置校验和费用上限**
- 只确认部署的签名和结果核对不够，另加：
  - 部署前用 `estimateGas`（或 `eth_call`）做干跑。
  - 设 `maxFeePerGas` 和 `gasLimit` 上限，超限转人工。
  - 工作器自己用固定编译器版本重算产物哈希，与记录不一致则拒绝。
  - "同一产物哈希已在 OP Sepolia 部署并铸造成功"作为 G2 的人工核对行。
- 与已定事项无冲突：这些是部署前的校验，不改变自动部署的决定。

**R17 ｜ 中 ｜ 可直接采纳 ｜ 对外接口没有限流声明，上传没有暂存总量上限**
- 问题：
  - 手册 3.1 第 6 节和审查第 8 项要求对外接口有输入校验和基本限流。计划只写了校验（`plan.md:177、183`）。
  - 自动审批没有数量上限，已定。但若令牌泄露或发件人被冒充，`prepare` 可以无限分配 100 MiB 的 Blob 对象，把免费额度打满。
  - `/api/media` 因 `no-store`（`plan.md:213`）每次读都回源 Blob，公开爬取也会耗额度。
- 修法：这是对上传和读取资源的保护，不是审批数量上限。
  - 单事件条目数和总字节上限、待拉取暂存总量上限，均可配置。达限时 `prepare` 返回 429 加短原因，进"需处理"，不静默丢弃。
  - 公开读取走 Vercel 防火墙限流规则（D1、G2 由维护者配置），或函数内计数。
  - D1.2 的额度估算把公开读取流量和调用数单列，并设 80% 告警。

**R18 ｜ 中 ｜ 可直接采纳 ｜ 收款地址配置的落点没写**
- 问题：`plan.md:70` 提到"固定接收公钥对应地址"，快照里有 `recipientConfigVersion`，"要求改收款地址"转人工。但凭据表没有它。
- 修法：
  - 写明存在数据库站点设置里（版本化，仅维护者在后台私下录入），或写进工作器配置。二者择一。
  - 测试和生产各一个，不进仓库。
  - 变更即新版本，旧批准失效。

**R19 ｜ 中 ｜ 【需要你决定】｜ "不做异地备份"是否也覆盖数据库本体**
- 问题：已定事项只写了不上链原图在 Contabo 一块盘上。免费 Supabase 项目没有托管备份，所以数据库本身也没有第二份。受影响的有审批记录、日记历史、操作键和凭证对账。手册 G2 门禁里的"备份恢复演练"在计划 G2 里没有对应条目。
- 推荐答案：接受。不新增备份。G2 把该门禁改写为"按决定豁免"，并写明丢库后哪些可从链上、Arweave 或私有 ZIP 恢复，哪些不可恢复。
- 请回答：是否确认范围包含数据库？

## 6. 无人值守时会卡住的地方

**R20 ｜ 高 ｜ 【需要你决定】｜ 单次 15 分钟节点与板块体量不匹配**
- 问题：手册 3.5.2 的 `implement` 节点是 `timeoutMs: 900000`，修复上限合计 3 次。地基含 0.1–0.9 共九张卡，memorial 和 permanent 各有数千行级工作。首夜很可能每块都在第一个 15 分钟节点超时，进入 `writeup`，或 3 次修复耗尽，整批变草稿。
- 手册把该字段含义标为【待验证】，不确定是单次调用还是整个会话的时限。
- 推荐 B：
  - D3 冒烟时先实测该字段的语义。
  - 地基和大板块的 `implement` 节点单独放宽 `timeoutMs`，例如 2–3 小时。
  - 要求 AI 按卡提交检查点，超时留下的是已推送的草稿进度。
  - 三次修复上限保持不变，熔断不缩水。
- 备选 A：`implement` 按卡链式拆成多个节点（同分支同 PR，每卡一次本卡测试）。但这会把修复总次数放大，需另行确认。
- 请回答：采用 B 还是 A？

**R21 ｜ 中 ｜ 可直接采纳 ｜ 任务卡里混有只能人做的步骤**
- 问题：例如 `plan.md:173` 的真实 Grok 投递、0.1 的"E2 在 Windows 打开本机首页"、各卡中的 E2/E3 演练。AI 会尝试做、`need_decision` 或卡住。
- 修法：
  - 每步标【AI 自动】或【人工·仅 F2/E2/E3，AI 不执行】。
  - 任务卡的"做完的定义"只含【AI 自动】。
  - C4 生成 `acceptance-script.md` 时沿用这套标记。

**R22 ｜ 中 ｜ 可直接采纳 ｜ 服务器工具链前置清单缺失**
- 问题：`agent` 无 sudo。夜间 AI 要跑定向 e2e、`forge test`、`sharp` 和 HEIC（`plan.md:49、90`），但没有前置清单。Playwright 的系统依赖需要 root 装，Foundry 要装，Node 24 要装，带 HEVC 的 libvips 也要装。
- 修法：
  - D3 前由管理用户装好并列清单。
  - `setup-worktree.sh` 的基线检查加一项"工具链就绪"，缺则明确报缺什么，而不是让 AI 空转重试。

## 7. 权限与上线风险

**R23 ｜ 中 ｜ 【需要你决定】｜ 公开读取与维护操作共用同一数据库角色**
- 问题：`plan.md:98` 的运行角色按"环境 × 网站或工作器"划分。公开页面、`/api/media` 和维护后台用同一个网站角色连库，RLS 分不出游客和维护者，隔离全靠应用代码。
- 核心承诺是明确不上链的照片不在前端展示。一旦公开路径代码有缺陷，同一连接能读到私有照片、历史和证据。
- 推荐：每环境再加一个只读角色，只有公开投影视图的 `SELECT`，公开路径用它连库，需要一个新变量。代价是 D1 多建两个角色。收益是与 `evaluateContentPolicy` 形成双保险。
- 请回答：是否采用？

**R24 ｜ 中 ｜ 可直接采纳 ｜ RLS 体检不能只靠 `db advisors`**
- 问题：`supabase db advisors` 的 RLS 规则主要面向 `public` 或已暴露的 schema，以实测为准。业务 schema 已被排除在 Data API 之外，E3 在测试 schema 临时建漏 RLS 的样表（`plan.md:136`）可能看不到红灯。
- 修法：
  - 在可信迁移脚本里写 RLS 断言：业务 schema 的每张表都启用 RLS。没有 `USING (true)` 类策略。`PUBLIC`、`anon`、`authenticated` 无授权。运行角色不是表所有者、无 `BYPASSRLS`。
  - E3 演练改为验证这个断言脚本本身会红。advisors 只当补充。

**R25 ｜ 中 ｜ 可直接采纳 ｜ 应用和工作器启动时不核对"连的是哪个库、哪个 schema"**
- 问题：迁移脚本会核对 `current_user` 和目标 schema，但网站和工作器没有。Preview 误配生产连接串，或测试工作器误指生产 schema，都只会静默读写，也是第 11 类风险的最后一道防线。
- 修法：在 `env.ts` 或连接初始化里，`VERCEL_ENV` 或工作器环境名映射到期望的 `(current_user, schema)`，不符则拒绝启动。

## 8. 同一件事发生两次，或做到一半中断

**R26 ｜ 中 ｜ 可直接采纳 ｜ Contabo 落盘与数据库引用之间崩溃会留孤儿，且是唯一副本**
- 问题：`plan.md:183、185` 只提到清理 Blob 孤儿。原图在 Contabo 上是唯一副本，落盘后、写库前崩溃会留下孤儿文件。

  - 先写临时文件并 fsync，再改名，再写库引用。
  - 启动时和每日对账：磁盘有文件、库无引用且超过 24 小时的，列入告警清单。因为是唯一副本，不自动删除。

## 9. "亮绿灯但没真测过"

**R27 ｜ 中 ｜ 可直接采纳 ｜ 现有 lint 挡不住几种常见作弊**
- 漏洞：
  - `test.fail()` 会把失败的测试记为通过。
  - 板块可以在逻辑里写 `process.env.CI` 或 `NODE_ENV === 'test'` 的假返回分支。
  - 测试文件可以直接引 `@playwright/test`，绕过公共 fixture（R14 的网络闸）。
- 修法：在 `eslint.config.mjs` 中：
  - 禁用 `test.fail`、`test.fixme`、`test.skip`、`test.describe.fixme`，确认现有 `no-skipped-test` 覆盖范围。
  - 用 `no-restricted-syntax` 禁止在 `src/lib/env.ts` 和适配器之外读取 `process.env.CI` 与 `NODE_ENV`。
  - 用 `no-restricted-imports` 要求 `e2e/features/**` 只能从受保护的 `e2e/support/` 引 `test`。

**R28 ｜ 中 ｜ 可直接采纳 ｜ 板块可事后删减自己的功能测试**
- 问题：锁定的验收 spec 通常只有一条黄金路径，板块的真实覆盖在 `e2e/features/<ID>/**`。后续的 `fix/<ID>-N` 可以把失败的测试删掉，`check-delivered` 也发现不了。
- 修法：guard 对已存在文件的 `e2e/features/**` 比较 `test(` 和 `test.describe(` 的出现次数，净减少则红灯。需要删除时由维护者走地基变更。

**R29 ｜ 低 ｜ 可直接采纳 ｜ `pnpm secrets` 不防"私下信息进公开仓库"**
- 问题：secretlint 不识别邮箱和 40 位十六进制地址，而需求和计划都要求这类信息不进仓库。
- 修法：给 `pnpm secrets` 附加拒绝规则：非 `example.*` 的邮箱，以及不在白名单文件内的 `0x` 加 40 位十六进制。真实猫名由 AI 本来就拿不到来兜底，不要把它写进任何扫描清单。

## 10. "好改动一直合不进去"

**R30 ｜ 中 ｜ 可直接采纳 ｜ 迁移时间戳"唯一递增"会让后合的 PR 反复被拒**
- 问题：`plan.md:130` 的 guard 核对"时间戳唯一递增"。两个板块并行时，先合并的 PR 抬高了最大时间戳，后合并的 PR 同步后时间戳不再递增，被 guard 拒绝。要改名并重新审核，消耗修复次数。
- 修法：guard 只核对"格式正确、全仓唯一、已存在文件未改"。应用顺序以合并顺序和台账为准。本地重放用同一顺序，由 `migrate-schema.mjs` 保证，不依赖文件名排序。

**R31 ｜ 中 ｜ 可直接采纳 ｜ Vercel 和 Actions 的配额与并发没有进入检查清单**
- 问题：
  - Hobby 套餐有每日部署次数上限和并发构建上限，数值以官方文档为准。
  - 两个 Vercel 项目接同一仓库，每次推送触发两套构建。三条线加同步重推，一晚可能触顶。触顶后所有必过的 Vercel 检查永远不出结果。
  - Hobby 条款限制个人非商业用途，而计划里有"客户"。
  - 若仓库私有，Actions 分钟数也是上限。需求原话写"仓库公开"，而 `plan.md:148` 写"私有仓库"，需统一。
- 修法：
  - D1 核对这三项，并把结果写进 `docs/intake-checklist.md`。
  - 需求原话为准，0.9 改成"仓库公开，规则集无需额外套餐"。若使用者实际改为私有，再核对 Actions 分钟数。
  - Playwright 浏览器、Foundry 做缓存，`ci.yml` 与 e2e 并发度设上限。

**R32 ｜ 中 ｜ 可直接采纳 ｜ `deployment_status` 的环境名可能匹配不上，PR 级 e2e 范围也未明**
- 问题 1：B.5 的条件写死 `environment == 'Preview'`。同一仓库接多个 Vercel 项目时，环境名可能带项目后缀，以实测为准。若匹配不上，`e2e` 作为必过检查永远不出结果。
- 修法 1：E2 先抓一次真实事件的 payload，把实际环境名和项目标识写入 `docs/field-notes.md`，再定工作流的筛选条件。
- 问题 2：`plan.md:47` 写"该提交的 Preview e2e"。没说 PR 上跑全部还是只跑自己的。
- 修法 2：PR 级跑 `e2e/acceptance`（已开启的开关）加本 PR 对应板块的 `e2e/features/<ID>`。完整 `pnpm e2e` 只在 `integration` 合并之后跑。这样别的板块不稳定的功能测试不会卡住无关 PR。

**R33 ｜ 低 ｜ 可直接采纳 ｜ `report/<日期>` PR 的 guard 特例和文件路径**
- guard 的所有权检查依赖 `modules.json`，而 `report/*` 与 `skin/*` 不在其中。给 `report/*` 写特例：只允许新增一个报告文件。
- 报告路径改为 `docs/run-reports/<日期>.md`，避免每批都改同一个 `docs/run-report.md` 而冲突。

## 11. 浏览器测试写数据：正式站触发与正式库

**R34 ｜ 中 ｜ 可直接采纳 ｜ 生产项目不出预览、e2e 只打测试站**

  - 加 R14 的"非同源请求中止"，并要求 `BASE_URL` 不等于生产 origin。
  - 配合 R25 的启动时库目标断言。
